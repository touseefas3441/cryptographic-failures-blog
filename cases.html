Case 1: Adobe Customer Data Breach

2013

In October 2013, Adobe announced that attackers had gained access to customer information and source code.

Adobe reported that customer IDs and encrypted passwords had been accessed. Information relating to approximately 2.9 million customers was also believed to have been removed, including names and encrypted payment card information.

Why is this relevant to cryptographic failures?

A later investigation by the Office of the Australian Information Commissioner found serious weaknesses in the protection of password information stored in an older backup system.

The system used encryption for passwords rather than the stronger password-hashing approach used in Adobe's newer authentication system. Password hints were also stored in plaintext.

What went wrong?

  • An older backup system continued to contain customer credentials.
  • Passwords in that system were encrypted rather than individually salted and hashed.
  • A single encryption key was used for the password information.
  • Password hints were stored in plaintext.
  • Some password hints could reveal the actual password or provide an obvious clue.

Potential impact

The combination of encrypted passwords and plaintext hints made it possible for security researchers to identify some common passwords. The exposed credentials could also create additional risk when users reused the same passwords on other websites.

Lesson from the case:

Sensitive credentials should be protected using security mechanisms appropriate for their purpose. Passwords should not simply be encrypted and stored like ordinary data. Secure password hashing and proper management of old systems are important parts of protecting user accounts.

Verified sources:

Adobe's original customer security announcement documented the 2013 incident and the information accessed.

The Office of the Australian Information Commissioner later investigated Adobe's security safeguards and documented the password-storage weaknesses.

Case 2: Debian OpenSSL Predictable Randomness

2006–2008

A different type of cryptographic failure occurred in Debian's OpenSSL package.

A Debian-specific change accidentally removed important code related to OpenSSL's random number generation. As a result, cryptographic random values became predictable.

Why is this a cryptographic failure?

Cryptographic systems depend on unpredictable random values when generating keys and other security material.

If the random values are predictable, an attacker may be able to guess or identify cryptographic keys that should have been secret.

What was affected?

Debian's security advisory stated that affected cryptographic material included:

  • SSH keys
  • OpenVPN keys
  • DNSSEC keys
  • X.509 certificate key material
  • SSL/TLS session key material

What did Debian recommend?

Debian recommended upgrading the affected OpenSSL packages and recreating cryptographic key material generated by vulnerable versions.

The affected keys could not simply be considered safe after the software was updated because keys generated using the vulnerable random number generator could already be predictable.

Lesson from the case:

Secure cryptography depends on more than selecting a strong algorithm. Random-number generation and implementation details are also critical. A strong algorithm can still provide weak protection if the secret values used by it are predictable.

Verified source:

Debian Security Advisory DSA-1571-1 documents the predictable random number generator vulnerability, CVE-2008-0166, the affected cryptographic material, and the required remediation.

What These Cases Have in Common

These incidents demonstrate two different ways cryptographic protection can fail.

Adobe: inappropriate password protection and weak handling of credential information.

Debian OpenSSL: predictable randomness resulted in cryptographic keys that could be guessed.

These examples show why secure cryptography requires correct algorithms, correct implementation, secure randomness, appropriate password protection, and proper key management.

Important Distinction

The cases above are documented historical incidents, not hypothetical examples created for this blog.
