Why Prevention Matters

Cryptographic failures can often be prevented by choosing appropriate cryptographic methods, protecting keys and secrets, securely storing passwords, and correctly configuring systems.

Security should be considered during application design rather than added only after a system has already been developed.

Main principle: Do not treat cryptography as simply "adding encryption". The entire process, including algorithms, keys, randomness, storage and configuration, needs to be considered.

1. Classify Sensitive Data

Developers should first understand what information their application collects, stores and transmits.

  • Identify sensitive personal information.
  • Identify authentication information.
  • Identify financial or payment information.
  • Identify confidential business information.
  • Determine which information actually needs to be retained.

Data that does not need to be stored should generally not be retained unnecessarily.

2. Use Strong and Appropriate Cryptography

Applications should use well-established cryptographic algorithms and protocols rather than creating their own cryptographic algorithms.

  • Use trusted and well-maintained cryptographic libraries.
  • Avoid deprecated algorithms and protocols.
  • Keep cryptographic libraries updated.
  • Use cryptography appropriate for the security requirement.
  • Review cryptographic configuration regularly.
Important: A strong algorithm can still be used incorrectly. Correct implementation and configuration are just as important.

3. Protect Data in Transit

Sensitive information travelling between a browser and a server should be protected using secure communication protocols.

Modern web applications normally use HTTPS with TLS to protect information during transmission.

  • Use HTTPS for sensitive web traffic.
  • Use current secure TLS configurations.
  • Disable obsolete protocols and weak cipher configurations.
  • Configure HTTP Strict Transport Security (HSTS) where appropriate.

4. Store Passwords Correctly

Passwords should not be stored as plaintext.

Passwords also should not normally be stored using reversible encryption. Password storage requires dedicated password-hashing methods designed to make large numbers of password guesses expensive.

Recommended concept:

User password → Password hashing algorithm → Salted password hash → Database

OWASP currently recommends strong adaptive password hashing algorithms such as Argon2id, bcrypt, or PBKDF2, with a unique salt for each password.

Fast general-purpose hashes such as SHA-256 should not be used by themselves for password storage because they allow password guesses to be performed very quickly.

5. Manage Cryptographic Keys Securely

Encryption is only useful if the encryption keys are properly protected.

  • Generate keys using secure cryptographic randomness.
  • Do not hard-code secret keys inside application source code.
  • Do not commit secret keys to public repositories.
  • Restrict access to cryptographic keys.
  • Rotate keys when required.
  • Have a process for replacing compromised keys.
  • Securely destroy keys when they are no longer required.

OWASP and NIST both emphasize the importance of key management throughout the cryptographic key lifecycle.

6. Use Secure Randomness

Cryptographic systems often depend on random values for keys, tokens, nonces and other security-related values.

These values must be generated using cryptographically secure random-number mechanisms rather than predictable values.

Example of a bad approach: Using predictable values such as timestamps, usernames or simple counters as secrets.

The Debian OpenSSL case discussed earlier demonstrates why predictable cryptographic randomness can create serious security problems.

7. Secure Development Practices

Cryptographic security should be included throughout the software development lifecycle.

  • Identify sensitive data during system design.
  • Create a threat model before implementation.
  • Use established cryptographic libraries.
  • Review cryptographic code carefully.
  • Keep dependencies updated.
  • Test security configurations.
  • Perform code reviews.
  • Monitor systems for security problems.
  • Have a plan for responding to compromised keys or secrets.

8. Quick Prevention Checklist

Security Area Recommended Practice
Sensitive data Identify and minimize unnecessary sensitive data.
Encryption Use trusted, current cryptographic algorithms and libraries.
Passwords Use salted adaptive password hashing.
Keys Generate, store, rotate and retire keys securely.
Randomness Use cryptographically secure random-number generation.
Network traffic Protect sensitive data using properly configured TLS.
Secrets Keep secrets outside source code and version control.
Maintenance Keep cryptographic libraries and security configurations updated.

Limitations

Following security recommendations does not guarantee that an application will never experience a security incident.

Cryptographic systems can still fail because of implementation errors, configuration mistakes, compromised keys, vulnerable dependencies, incorrect assumptions or weaknesses elsewhere in the application.

For this reason, cryptography should be treated as one part of a broader security strategy rather than as a complete solution by itself.

Key lesson: Good cryptography requires good implementation, configuration, key management and ongoing security review.
